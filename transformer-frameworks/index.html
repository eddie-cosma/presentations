Part 1

Transformation basics

What is data integration?

  • Data transformation is part of data integration
  • Raw data is extracted from disparate sources
  • Extracted data is loaded into an accessible location (e.g., database, flat files)
  • Data is transformed into a usable format
The classic picture. Note the ordering assumption baked into the acronym.

ETL or ELT?

Transform can come before or after load.

ETL

  • Transform in flight, in a separate compute layer
  • Warehouse only ever sees clean data
  • Expensive to re-run; source data not retained

ELT

  • Land raw data first, transform in the warehouse
  • Cheap storage + elastic compute made this the default
  • Raw data stays available to re-transform
dbt and SQLMesh are both the “T” in ELT. They assume your data is already in a warehouse and they push work down to that warehouse as SQL.
Important framing: neither tool moves data. Neither is an ingestion tool. They generate and execute SQL against a warehouse you already have.

What is data transformation?

Doing whatever you need to do to your data to make it usable for reporting or downstream applications. E.g.,

  • Cleaning up bad or missing data
  • Joining multiple raw datasets
  • Deriving new data
  • Translating coded values
  • Fixing data types (like dates encoded as strings)
  • Many more…

Use cases for data transformation

  • Business intelligence – dashboards, reporting
  • Data warehousing – turning raw source tables into a coherent model
  • Machine learning
  • Data migration – reshaping data to fit a new system's schema

Source: ibm.com/think/topics/data-transformation

Data transformation steps

  • Data discovery – understanding dataset structure, characteristics
  • Data mapping – defining how individual fields fit into final output
  • Code generation – defining executable code to actually transform data
  • Code execution – executing the generated code
  • Data review – make sure it all went right
We are primarily concerned with code generation and code execution.

A word about transformation tools

All kinds of technologies can be used to transform data…

  • awk can transform data
  • vim can transform data
  • Excel can transform data
  • pandas can transform data
  • Regular expressions can transform data

Important considerations

To be robust, transformation workflows should be:

  • Validatable (testable)
  • Repeatable (consistent)
  • Automatable (fast)
  • Iterable (code-based and version tracked)

Popular frameworks

Frameworks developed to make transformations fit our criteria

SQL-based

  • Data build tool (dbt)
  • SQLMesh
  • Dataform

Python-native

  • Dagster
  • Prefect
  • Kedro
  • Ibis

Again, there are many more…

We are going to focus on dbt and SQLMesh.

Worth noting the Python-native list blurs the line between transformation and orchestration — Dagster and Prefect are orchestrators that can transform.

Part 2

dbt

What is dbt?

  • Data build tool — the transformation layer of the “modern data stack”
  • Started in 2016; effectively the default answer for SQL transformation today
  • A Python CLI that turns a directory of SELECT statements into a dependency-ordered set of tables and views in your warehouse
  • Brings software engineering practice to analytics:
    • version control
    • code review
    • environments
    • tests
    • documentation
    • modularity

dbt basics: the model

A model is one .sql file containing one SELECT. The file name is the table name.


-- models/staging/stg_orders.sql

select
    id                  as order_id,
    user_id             as customer_id,
    order_date,
    status,
    amount_cents / 100.0 as amount_usd
from raw.orders
where status != 'deleted'

dbt wraps this in DDL for you


create or replace view analytics.stg_orders as (
    select ... /* your SELECT, verbatim */
);

dbt templating: Jinja

dbt files are Jinja templates that happen to contain SQL. Before execution, dbt renders the template into a plain SQL string.

SyntaxMeaning
{{ ... }}Expression — renders a value into the SQL
{% ... %}Statement — control flow, macro definitions, no output
{# ... #}Comment — stripped before compilation
Jinja is string templating.
Same templating engine as Flask/Django-ish templates. It's textual substitution.

Jinja: ref and source

Two functions do most of the work in a real dbt project.


-- staging model reads a RAW table via source()
select *
from {{ source('jaffle', 'orders') }}

-- compiles to: from raw_jaffle.orders

-- downstream model reads another MODEL via ref()
select *
from {{ ref('stg_orders') }}

-- compiles to: from analytics_dev_eddie.stg_orders
  • ref() returns the right name for the current environment (dev vs. prod)
  • ref() is also how dbt discovers the DAG
Key insight: the dependency graph is a side effect of a templating function. dbt knows model A depends on model B, but not which *columns* flow between them.

Jinja: macros

A macro is a function that returns a SQL fragment. This is dbt's abstraction mechanism.


-- macros/cents_to_dollars.sql
{% macro cents_to_dollars(column_name, precision=2) %}
    round({{ column_name }} / 100.0, {{ precision }})
{% endmacro %}

-- models/staging/stg_payments.sql
select
    payment_id,
    {{ cents_to_dollars('amount') }} as amount_usd,
    {{ cents_to_dollars('tip') }}    as tip_usd
from {{ source('stripe', 'payments') }}

Jinja: control flow

Because it's a full templating language, you can generate SQL programmatically.


{% set payment_methods = ['credit_card', 'paypal', 'bank_transfer'] %}

select
    order_id,
    {% for method in payment_methods %}
    sum(case when payment_method = '{{ method }}'
             then amount_usd else 0 end) as {{ method }}_amount
    {%- if not loop.last %},{% endif %}
    {% endfor %}
from {{ ref('stg_payments') }}
group by 1

dbt basics: materializations

The same SELECT becomes a different physical object depending on config.

MaterializationWhat dbt does
viewCREATE VIEW
tableCREATE TABLE AS, dropped and rebuilt each run
incrementalInsert/merge only new rows
ephemeralInlined as a CTE, never persisted

{{ config(materialized='table') }}

select ...

dbt example: a small project

Declare the raw sources, with freshness expectations and tests:


# models/staging/_sources.yml
version: 2
sources:
  - name: jaffle
    schema: raw_jaffle
    tables:
      - name: orders
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}
        loaded_at_field: _loaded_at
        columns:
          - name: id
            data_tests:
              - unique
              - not_null
OPTIONAL — safe to skip if running long. The freshness block is the interesting part; everything else is boilerplate.

dbt example: staging model


-- models/staging/stg_orders.sql
{{ config(materialized='view') }}

select
    id                   as order_id,
    user_id              as customer_id,
    cast(order_date as date) as order_date,
    lower(status)        as status,
    {{ cents_to_dollars('amount_cents') }} as amount_usd
from {{ source('jaffle', 'orders') }}
where status != 'deleted'

Convention: stg_* models are 1:1 with a source table

dbt example: mart model


-- models/marts/fct_customer_orders.sql
{{ config(materialized='table') }}

with orders as (
    select * from {{ ref('stg_orders') }}
),
customers as (
    select * from {{ ref('stg_customers') }}
)

select
    c.customer_id,
    c.customer_name,
    count(o.order_id)      as order_count,
    sum(o.amount_usd)      as lifetime_value,
    min(o.order_date)      as first_order_date
from customers c
left join orders o on o.customer_id = c.customer_id
group by 1, 2

dbt example: tests

Data tests — assertions run against real, built data.


# models/marts/_models.yml
models:
  - name: fct_customer_orders
    columns:
      - name: customer_id
        data_tests:
          - unique
          - not_null
      - name: lifetime_value
        data_tests:
          - dbt_utils.accepted_range:
              min_value: 0

Unit tests (dbt 1.8+) — fixed inputs, expected outputs, no warehouse data needed.


unit_tests:
  - name: test_amount_conversion
    model: stg_orders
    given:
      - input: source('jaffle', 'orders')
        rows:
          - {id: 1, amount_cents: 1050,
             status: 'SHIPPED'}
    expect:
      rows:
          - {order_id: 1, amount_usd: 10.50,
             status: 'shipped'}
Data tests are post-hoc: build it, then query it and see if the query returns rows. Unit tests arrived in 2024, six years after the tool.

dbt example: running it


# build everything, in dependency order
$ dbt run

# run models + tests + seeds + snapshots together
$ dbt build

# just this model and everything downstream of it
$ dbt build --select stg_orders+

# only what changed vs. the last production run
$ dbt build --select "state:modified+" --state ./prod-artifacts

# generate and serve the docs site (DAG viewer)
$ dbt docs generate && dbt docs serve
OPTIONAL — safe to skip if running long. Note the state: selector — it needs you to stash and pass the previous run's manifest.json yourself. Remember this when we get to SQLMesh plan.

The incremental model


{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}

select * from {{ ref('stg_orders') }}

{% if is_incremental() %}
  -- only on incremental runs, not the first build
  where order_date > (select max(order_date) from {{ this }})
{% endif %}
  • The model now behaves differently in dev than in prod
  • max(order_date) from the target is a proxy for “what's missing”
  • Miss a day of runs? Nothing tells you. There's no record of which intervals were loaded
  • Need to backfill last March? --full-refresh the whole table, or hand-write a one-off
This slide is the hinge of the whole talk. Every pain point SQLMesh addresses is visible right here.

What could be better?

  • Better "understanding" of SQL
  • Better handling of incremental runs/state
  • Easier dev vs. prod environment management

A decade of transformation frameworks

The dbt era

  • March 9, 2016dbt's first commit, under RJMetrics
  • January 2017Sinter launches (future dbt Cloud)
  • April 2020Series A funding
  • November 2020Series B funding
  • June 2021Series C funding
  • February 2022Series D funding… $4.2B valuation

A new foe has appeared?

  • September 2022SQLMesh's first commit (Tobiko Data)
  • May 2025dbt Fusion announced under ELv2, not OSI open source
  • September 2025Fivetran acquires Tobiko Data (SQLMesh, Tobiko Cloud)
  • October 13, 2025Fivetran + dbt Labs merger announced
  • March 25, 2026Fivetran contributes SQLMesh to the Linux Foundation

Walk this left to right. The punchline: as of mid-2026 the same company owns both frameworks — and has open-sourced or donated both of them.

The commercialization worry

  • May 2025: dbt Labs announces Fusion — a from-scratch rewrite of dbt in Rust that actually parses SQL. Released under ELv2: free to use, but not OSI open source, and you can't build a hosted dbt on it
  • The reaction: is dbt Core now the slow, deprecated tier? Was the community's work the on-ramp to a proprietary engine?
  • Then the acquisitions: Fivetran buys Tobiko Data, then merges with dbt Labs. One vendor, both frameworks
  • June 1, 2026: dbt Core v2.0 alpha — the Fusion engine, relicensed Apache 2.0. One engine for OSS and commercial distributions
The worry that motivated this talk was largely answered in June — but only after a year of uncertainty, and only under a single vendor's control.
Be intellectually honest: the licensing story resolved better than most people feared. The concentration story did not.

Part 4

SQLMesh

What is SQLMesh?

  • An open-source (Apache 2.0) Python transformation framework, first committed September 2022 by Tobiko Data
  • Now governed by the Linux Foundation (March 2026)
  • Deliberately dbt-shaped on the surface: SQL files, a DAG, tests, environments, a CLI
  • Radically different underneath: it parses and understands your SQL
The one-sentence version: SQLMesh treats SQL as code to be compiled, not text to be templated — and uses that understanding to tell you what your change will break before you run it.

The foundation: SQLGlot

SQLMesh is built on SQLGlot, a pure-Python SQL parser, transpiler, and optimizer covering 20+ dialects.


>>> import sqlglot
>>> sqlglot.parse_one("SELECT a FROM tbl").sql()
'SELECT a FROM tbl'

>>> sqlglot.parse_one("SELECT a FROM tbl")
Select(expressions=[Column(this=Identifier(this=a))], from=From(...))

>>> sqlglot.transpile(
...     "SELECT EPOCH_MS(1618088028295)", read="duckdb", write="snowflake"
... )
["SELECT TO_TIMESTAMP(1618088028295 / 1000)"]
  • Your SQL becomes an abstract syntax tree, not a string
  • That makes column-level lineage, semantic diffs, and cross-engine transpilation possible
  • Typos and invalid column references are caught at plan time, without touching the warehouse
SQLGlot predates SQLMesh and is used well outside it. It's the enabling technology for everything that follows.

SQLMesh basics: the model

A model is a SQL file too — but it opens with a declarative MODEL block.


MODEL (
  name analytics.stg_orders,
  kind VIEW,
  cron '@daily',
  grain order_id,
  audits (
    unique_values(columns := (order_id)),
    not_null(columns := (order_id, customer_id))
  )
);

SELECT
  id::INT                  AS order_id,
  user_id::INT             AS customer_id,
  order_date::DATE         AS order_date,
  LOWER(status)            AS status,
  amount_cents / 100.0     AS amount_usd
FROM raw.orders
WHERE status != 'deleted'

Note: no ref(). You write the real table name and SQLMesh resolves it per environment — it knows what a table reference is.

SQLMesh basics: model kinds

Instead of materializations plus hand-written logic, you declare the semantics.

KindMeaning
VIEWA view, rebuilt on change
FULLRebuilt from scratch every run
INCREMENTAL_BY_TIME_RANGERows belong to time intervals; SQLMesh tracks which intervals exist and fills gaps
INCREMENTAL_BY_UNIQUE_KEYUpsert on a key
SCD_TYPE_2_BY_TIME / _COLUMNSlowly changing dimension history, built in
SEEDA CSV loaded as a table
EMBEDDEDInlined as a CTE (dbt's “ephemeral”)
The important shift: SCD Type 2 and incrementality are first-class kinds, not patterns you assemble out of macros.

Incremental models, declared


MODEL (
  name analytics.fct_orders,
  kind INCREMENTAL_BY_TIME_RANGE (
    time_column order_date,
    batch_size 30
  ),
  start '2024-01-01',
  cron '@daily',
  grain order_id
);

SELECT *
FROM analytics.stg_orders
WHERE order_date BETWEEN @start_ds AND @end_ds
  • No is_incremental() branch — the model runs the same way in dev and prod
  • @start_ds / @end_ds are the interval being processed, supplied by the framework
  • SQLMesh records which intervals have been loaded in its state database
  • Missed three days? It knows, and backfills exactly those three days
  • Want to reload March? sqlmesh plan --restate-model analytics.fct_orders --start 2026-03-01 --end 2026-03-31
Contrast this directly with the earlier dbt incremental slide. Same job, and the framework is now responsible for correctness instead of the analyst.

Virtual data environments

The idea that makes everything else work: separate the names people query from the tables that hold data.

Virtual layer — views

prod.fct_orders
prod.stg_orders
dev_eddie.fct_orders
dev_eddie.stg_orders
→

Physical layer — tables

stg_orders__a1f9c2
fct_orders__7bd104
stg_orders__c8e330  (new)
  • A new environment is just a set of views pointing at existing tables — created in seconds, costs nothing
  • Change one model, and only that model gets a new physical table (fingerprinted by its snapshot)
  • Promoting to prod = repointing views. No rebuild, no downtime, instant rollback
The killer consequence: the table your dev environment validated is the *exact same table* that prod will point at. You are not rebuilding and hoping it matches.

Plan: what would change?

If you've used Terraform, you already know this workflow.


$ sqlmesh plan dev

Differences from the `dev` environment:

    └── Indirectly Modified Children:
        └── analytics.fct_orders

---

Three things to point at: the semantic diff of the SQL itself, the automatic breaking/non-breaking classification, and the fact that nothing has run yet.

Models needing backfill:
└── analytics.stg_orders: [2024-01-01 - 2026-08-10]

$ sqlmesh plan prod

Differences from the `prod` environment:
└── analytics.stg_orders (Non-breaking)

Apply - Virtual Update [y/n]: y
Virtually updating 'prod'   ━━━━━━━━━━ 100%
The target environment has been updated successfully  (0.4s)
Promoting to prod re-used the table dev already validated. No backfill. Sub-second. That is the whole point of the virtual layer.
The second command is the payoff. In dbt, promoting to prod means running the models again in prod and hoping the result matches what you saw in dev.

Breaking vs. non-breaking

SQLMesh diffs the AST, not the text, and classifies every change.

Non-breaking

  • Adding a column no one downstream reads
  • Changing a comment or formatting
  • Result: rebuild only this model; children keep their existing tables

Breaking

  • Changing the logic behind a column that downstream models consume
  • Removing or retyping a referenced column
  • Result: rebuild this model and the affected children
You can always override the classification. But the default is computed from column-level lineage — and the compute you don't spend is real money.
In dbt this decision is made by a human with a `--select model+` and a guess.

Forward-only and dev previews

  • Forward-only plans — for huge tables you can't afford to rebuild: apply the change going forward, leave history as-is
  • Dev previews — SQLMesh can build a dev version over a small date window, so you validate on a day of data, not five years
  • sqlmesh table_diff prod:dev analytics.fct_orders — row and column level data diff between two environments, before you merge

$ sqlmesh plan dev --start '2026-08-01' --end '2026-08-10'
$ sqlmesh table_diff prod:dev analytics.fct_orders --show-sample
This is the answer to “my dev run costs $400 and takes two hours.”
OPTIONAL — safe to skip if running long. table_diff is the one to mention if you only have time for a sentence.

Testing: audits and unit tests

Audits — assertions against built data (dbt's data tests), declared inline or reusable.


-- audits/no_negative_amounts.sql
AUDIT (
  name assert_positive_amount,
  dialect duckdb
);

SELECT *
FROM @this_model
WHERE amount_usd < 0

Unit tests — fixture in, expected out. Run in milliseconds against DuckDB, no warehouse needed.


test_stg_orders:
  model: analytics.stg_orders
  inputs:
    raw.orders:
      - id: 1
        amount_cents: 1050
        status: 'SHIPPED'
  outputs:
    query:
      - order_id: 1
        amount_usd: 10.50
        status: 'shipped'

sqlmesh test runs unit tests; audits run automatically as part of plan and run, and can block a promotion.

Unit tests were in SQLMesh from very early on, not bolted on six years later.

Python models and macros

When SQL isn't enough, drop into Python — a first-class model type, not an escape hatch.


from sqlmesh import model, ExecutionContext
import pandas as pd
import typing as t
from datetime import datetime

@model(
    "analytics.customer_segments",
    columns={"customer_id": "int", "segment": "text"},
    kind="FULL",
    cron="@daily",
)
def execute(
    context: ExecutionContext,
    start: datetime,
    end: datetime,
    execution_time: datetime,
    **kwargs: t.Any,
) -> pd.DataFrame:
    table = context.resolve_table("analytics.fct_customer_orders")
    df = context.fetchdf(f"SELECT customer_id, lifetime_value FROM {table}")
    df["segment"] = pd.cut(df.lifetime_value, [0, 100, 1000, 1e9],
                           labels=["low", "mid", "whale"])
    return df[["customer_id", "segment"]]

Python macros (@macro) also exist — but they manipulate the SQL AST, so SQLMesh still understands the result. Jinja is supported for dbt compatibility.

OPTIONAL — safe to skip if running long. For a Python meetup this one usually earns its place — keep it if the room is engaged.

Built-in scheduling

  • Every model declares its own cron — cadence is a property of the model, not of an external DAG you maintain in parallel
  • sqlmesh run evaluates whatever is due, fills any missing intervals, and stops
  • Put that one command on cron/systemd/GitHub Actions and you have a scheduler
  • Or plug into Airflow, Dagster, or Prefect when you need to sit inside a bigger pipeline

$ sqlmesh run          # run what's due, backfill any gaps
$ sqlmesh ui           # browser IDE: editor, DAG, column-level lineage
$ sqlmesh dlt_refresh  # / sqlmesh migrate, format, lint, audit, test ...
dbt Core needs an orchestrator to be useful in production. SQLMesh ships with enough scheduling to not need one on day one.

SQLMesh runs your dbt project

Migration isn't all-or-nothing — SQLMesh can read a dbt project directly.


# point SQLMesh at an existing dbt project
$ sqlmesh init -t dbt
$ sqlmesh plan
# refs, sources, macros, seeds, tests, and profiles.yml are read as-is

# or convert the project to native SQLMesh models
$ sqlmesh migrate
  • You keep your Jinja, your ref()s, and your dbt packages
  • You gain virtual environments, plan/apply, and interval tracking
  • Coverage is good but not total — exotic macros and adapter-specific tricks need review
This was a deliberate adoption strategy: meet dbt users where they are.

The philosophical difference

dbt

  • SQL is text to be templated
  • The framework orchestrates; the human owns correctness
  • Optimizes for approachability and ecosystem
  • Conventions over guarantees

SQLMesh

  • SQL is code to be compiled
  • The human declares intent; the framework owns correctness
  • Optimizes for safety and compute cost
  • Guarantees over conventions
Notice that dbt v2/Fusion — Rust, real SQL parsing, column-level lineage, state-aware orchestration — is converging on SQLMesh's thesis. SQLMesh won the argument. It's less clear that it won the market.
This is the line to land the talk on. Say it slowly.

Where does that leave us?

  • SQLMesh offers a promising technological advancement on transformation framework design
  • SQLMesh development activity decreased dramatically after Tobiko Data was acquired by Fivetran

Weekly commits, SQLMesh repo — the cliff is the September 2025 acquisition.

Let this chart sit for a beat. It's the single most persuasive slide in the deck.

Where does that leave us? (cont.)

  • The SQLMesh donation to the Linux Foundation is promising, but it's too early to tell the direction things will go
  • Neutral governance is not the same as engineering investment. Named members are on board; sustained contribution is the thing to watch
  • Meanwhile dbt Core v2 answered the licensing complaint — Apache 2.0, one engine, no OSS/commercial split in the runtime
  • For now, dbt Core is still the safe bet for new projects if a transformation framework is desired
The irony worth sitting with: the talk that started as “dbt is over-commercializing, here's the alternative” ends with both projects owned or seeded by the same company, and both under permissive licenses.

So which should you pick?

Reach for dbt when…

  • You're starting fresh and want the shortest path to value
  • Your team is SQL-literate but not engineering-heavy
  • You depend on the package/integration ecosystem
  • You need to hire for it
  • Your warehouse bill isn't the problem

Reach for SQLMesh when…

  • Rebuild cost is a real line item
  • You have many contributors and need change safety
  • Correct backfills and late-arriving data actually matter
  • You're multi-engine, or expect to migrate engines
  • You want scheduling without standing up Airflow
And a third option: run SQLMesh on your existing dbt project for a week. It's the cheapest way to find out which set of problems you actually have.

Demos

Demo 1 — dbt

  1. Tour the project: models/, _sources.yml, a staging model, a mart
  2. dbt build — watch the DAG execute in dependency order
  3. Show target/compiled/ — the Jinja is gone, it's just SQL

  6. Introduce a genuinely breaking change — watch the classification flip
  7. sqlmesh ui — column-level lineage

Takeaways

  • Transformation frameworks exist to make SQL validatable, repeatable, automatable, and iterable
  • dbt made that mainstream by treating SQL as templated text
  • SQLMesh argued the framework should understand your SQL — and got virtual environments, semantic change detection, and correct backfills out of it
  • In 2026 both live under Apache 2.0, and dbt v2 has adopted much of SQLMesh's thesis
  • Pick dbt for ecosystem and momentum; pick SQLMesh when correctness and compute cost are the constraint
